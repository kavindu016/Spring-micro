## Containerization

The microservices application is containerized using **Docker** to provide consistent, isolated, and portable environments for each service.

The containerization process was implemented in multiple stages. Initially, a simple Dockerfile was used for one service. Then, a multi-stage Docker build using Spring Boot's layered JAR feature was introduced to optimize the image. Finally, **Jib Maven Plugin** was adopted to simplify containerization across all six microservices.

---

### 1. Initial Dockerization

Initially, the application was containerized using a simple Dockerfile based on the **Eclipse Temurin JRE 21** image.

```dockerfile
FROM eclipse-temurin:21-jre

COPY target/*.jar app.jar

ENTRYPOINT ["java", "-jar", "app.jar"]
```

The application JAR generated by Maven is copied directly into the Docker image and executed when the container starts.

Although this approach is simple, the resulting Docker image was relatively large because the complete Spring Boot JAR was copied into the image as a single unit.

---

### 2. Multi-Stage Containerization with Spring Boot Layers

To improve the Docker image structure, a **multi-stage Docker build** was tested using Spring Boot's **Layered JAR** functionality.

```dockerfile
FROM eclipse-temurin:21-jdk AS builder

WORKDIR /app

COPY target/*.jar app.jar

RUN java -Djarmode=layertools -jar app.jar extract


FROM eclipse-temurin:21-jre

WORKDIR /app

COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./

ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
```

#### Build Stage

The first stage uses the **JDK** image:

```dockerfile
FROM eclipse-temurin:21-jdk AS builder
```

The previously generated Spring Boot JAR is copied into the builder stage:

```dockerfile
COPY target/*.jar app.jar
```

Spring Boot's `layertools` is then used to extract the JAR into separate layers:

```dockerfile
RUN java -Djarmode=layertools -jar app.jar extract
```

The JAR is separated into layers such as:

```text
dependencies/
spring-boot-loader/
snapshot-dependencies/
application/
```

#### Runtime Stage

The second stage uses the smaller **JRE** image:

```dockerfile
FROM eclipse-temurin:21-jre
```

Only the required application layers are copied from the builder stage:

```dockerfile
COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./
```

The application is started using Spring Boot's `JarLauncher`:

```dockerfile
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
```

#### Benefits

This approach provides:

* **JDK/JRE separation** – The JDK is used only in the builder stage.
* **Smaller runtime environment** – The final image contains the JRE rather than the JDK.
* **Layer-based caching** – Dependencies and application code are separated into different layers.
* **Faster rebuilds** – Unchanged dependency layers can be reused when application code changes.
* **Reduced duplication** between build-time and runtime environments.

This approach was initially tested on one microservice.

### 3. Containerizing All Microservices with Jib

The project contains **six microservices**. Creating and maintaining a separate Dockerfile for every service would introduce duplicated configuration and additional maintenance.

Therefore, **Google Jib Maven Plugin** was introduced to simplify the containerization process.

Jib allows container images to be built directly through Maven without requiring a Dockerfile.

The Jib configuration was added to the **parent `pom.xml`**, allowing the microservices to inherit the same containerization configuration.

```xml
<plugin>
    <groupId>com.google.cloud.tools</groupId>
    <artifactId>jib-maven-plugin</artifactId>
    <version>3.4.4</version>

    <configuration>
        <from>
            <image>eclipse-temurin:21-jre</image>
        </from>

        <to>
            <image>registry.hub.docker.com/kavindu20/${project.artifactId}</image>
        </to>
    </configuration>
</plugin>
```

### Jib Configuration

#### Base Image

```xml
<from>
    <image>eclipse-temurin:21-jre</image>
</from>
```

The `from` configuration specifies the **base image** used for the container.

The project uses **Eclipse Temurin JRE 21** as the runtime environment for the Spring Boot microservices.

#### Docker Hub Image Name

```xml
<to>
    <image>registry.hub.docker.com/kavindu20/${project.artifactId}</image>
</to>
```

The `to` configuration specifies the Docker Hub repository where the generated image will be pushed.

```text
kavindu20
```

is the Docker Hub username/namespace.

The `${project.artifactId}` variable is automatically replaced with the artifact ID of each microservice.

For example:

```xml
<artifactId>order-service</artifactId>
```

produces:

```text
kavindu20/order-service
```

while:

```xml
<artifactId>inventory-service</artifactId>
```

produces:

```text
kavindu20/inventory-service
```

Therefore, each microservice automatically receives a **unique Docker image name**.

### 4. Docker-Specific Application Configuration

Since the application contains multiple microservices, some configuration values need to change when the services run inside Docker.

For this reason, each microservice contains a separate:

```text
application-docker.properties
```

file.

The standard `application.properties` is used for the local environment, while `application-docker.properties` contains configuration specific to the Docker environment.

### Local vs Docker Configuration

When running services locally, one service may communicate with another using `localhost`:

```properties
inventory.service.url=http://localhost:8082
```

However, inside Docker, `localhost` refers to the **current container itself**.

Therefore, when the services communicate through Docker, the Docker service name is used instead:

```properties
inventory.service.url=http://inventory-service:8082
```

For example:

```text
Local Environment
       │
       ▼
localhost:8082
       │
       ▼
Inventory Service


Docker Environment
       │
       ▼
inventory-service:8082
       │
       ▼
Inventory Service Container
```

The same principle is applied to other environment-specific configurations, such as:

* `localhost` → Docker service name
* Local service ports → Docker internal ports
* Local database host → Database service name
* Local service URLs → Docker service URLs
* Other Docker-specific connection properties

### Example Project Structure

Each microservice contains its own Docker-specific configuration:

```text
service/
└── src/
    └── main/
        └── resources/
            ├── application.properties
            └── application-docker.properties
```

The Docker profile can be activated using:

```bash
java -jar app.jar --spring.profiles.active=docker
```

This allows the application to use the Docker-specific configuration without modifying the application source code.

### Why Separate Configuration is Used

Using `application-docker.properties` keeps the local and Docker environments separate.

```text
                  Spring Boot Service
                         │
              ┌──────────┴──────────┐
              │                     │
              ▼                     ▼
 application.properties    application-docker.properties
              │                     │
              ▼                     ▼
       Local Environment      Docker Environment
              │                     │
              ▼                     ▼
      localhost:port          service-name:port
```

This allows the same application code to run in both environments while only changing the environment-specific configuration.

### 5. Building and Pushing All Images

Because the Jib configuration is defined in the parent POM, the container images for all six microservices can be created from the **parent/root project directory**.

The following Maven command is used:

```bash
mvn clean compile jib:build
```

This command:

1. Cleans previous Maven build artifacts.
2. Compiles the microservices.
3. Uses Jib to create container images.
4. Generates an image name using each service's `artifactId`.
5. Authenticates with Docker Hub.
6. Pushes the generated images to Docker Hub.


All six images can therefore be built and pushed using a **single Maven command**.

---

### 6. Docker Hub Authentication

Before pushing images to Docker Hub, Maven needs authentication credentials.

The Docker Hub credentials are configured in Maven's `settings.xml`.

```xml
<settings xmlns="http://maven.apache.org/SETTINGS/1.0.0"
          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
          xsi:schemaLocation="http://maven.apache.org/SETTINGS/1.0.0 http://maven.apache.org/xsd/settings-1.0.0.xsd">

    <servers>
        <server>
            <id>registry.hub.docker.com</id>
            <username>kavindu20</username>
            <password>DOCKER_HUB_ACCESS_TOKEN</password>
        </server>
    </servers>

</settings>
```

The `<password>` field contains a **Docker Hub Access Token**, rather than the Docker Hub account password.

The `<id>` in `settings.xml` corresponds to the Docker registry used by the Jib configuration.

> **Security:** `settings.xml` containing the actual Docker Hub access token must not be committed to GitHub. It should be kept locally or provided securely through CI/CD secrets.

                                  │
                                  ▼
                         6 Microservices
                                  │
                                  ▼

                                  │

                                  │
                  ┌───────────────┴───────────────┐
                  │                               │
                  ▼                               ▼
        Eclipse Temurin 21 JRE       ${project.artifactId}
          Base Runtime Image             Unique Image Name
                  │                               │
                  └───────────────┬───────────────┘
                                  │
                                  ▼
                        mvn clean compile jib:build
                                  │
                                  ▼
                         Jib builds images
                                  │
                                  ▼
                      Docker Hub Authentication
                         using Access Token
                                  │
                                  ▼
                            Docker Hub
                                  │
             ┌────────────────────┼────────────────────┐

          Image 1              Image 2              Image 3
             │                    │                    │
